# Силовой периметр СЗФО × продукты Сбера

Демонстрационная модель приоритизации розничных и b2g-продуктов Сбера
в силовом сегменте Северо-Западного федерального округа. Считает
потенциал (0–100) для каждой пары (ведомство × продукт) на основе
публикаций, экспертной позиции Сбера и данных рынка.

Публичная страница проекта:
`https://<username>.github.io/<repo-name>/`
(GitHub Pages, деплой автоматический из `main`).

**Демо-модель. Не оферта. Не заменяет коммерческую проработку.**

---

## Что внутри

- **12 ведомств** силового периметра СЗФО (МВД, МО/ЛВО, ВМФ, Росгвардия,
  МЧС, ФСИН, ФССП, ФТС, СК, Прокуратура — федеральный и региональный уровень).
- **15 продуктов Сбера**: 10 core (зарплатные проекты, ипотека, потреб,
  НПФ, премиум, ДБО, эквайринг, GigaChat, облако, кибербез) + 5 eco
  (СберПрайм, Спасибо, Самокат/Купер, Здоровье, Мобайл).
- **180 сегментных ячеек** со скором, разложением формулы и списком
  источников.
- **Конкурентная матрица розницы**: реальные ставки, УТП, слабости
  продуктов ВТБ, ГПБ, ПСБ, Почта Банка, Совкомбанка, Т-Банка, ДОМ.РФ,
  Альфа-Банка. Обновляется еженедельно.
- **Плейбуки по типу ведомства** — тактика захода с указанием того, за
  что не биться (например, СОГАЗ для МО).

## Методология

Полное описание — [`docs/METHODOLOGY.md`](docs/METHODOLOGY.md).

Краткие пояснения к терминам, которые видит пользователь на странице:

### Скоринг

Расчёт потенциала (0–100) по формуле из 5 множителей:

- **f_demand** — сила спроса из публикаций. Складывается из «событийных
  триггеров» (объявленный набор личного состава, индексация довольствия,
  тендеры и т.д.). Каждый триггер даёт вклад в demand_signal только для
  тех продуктов, к которым он привязан.
- **f_position** — позиция Сбера в сегменте. Экспертная оценка,
  откалибрована по долям рынка (Frank RG, Эксперт РА, banki.ru).
- **f_size** — масштаб клиента = штат / 30 000.
- **f_sent** — сентимент публикаций, размеченный LLM по паре
  (ведомство × сегмент), минимум 5 источников для валидности.
- **f_comp** — поправка на конкуренцию, взвешенная по долям банков-конкурентов.

Формулы:
- core-продукты: `f_demand·0.30 + f_position·0.25 + f_size·0.20 + f_sent·0.15 + f_comp·0.10`
- eco-продукты: `f_size·0.35 + f_position·0.30 + f_demand·0.10 + f_sent·0.05 + f_comp·0.05 + anchor`

Разложение формулы для каждой ячейки доступно в UI: наведите курсор,
нажмите кнопку «?».

### Сентимент

Тональность публикаций (−1..+1) в контексте *способности ведомства
платить и открытости к внешним сервисам*, а НЕ общий тон новости.
Метод — LLM-разметка (GigaChat / локальная модель) по трёхбалльной
шкале с явной системной инструкцией. При количестве публикаций < 5
берётся нейтраль (0.5) и ячейка помечается «⊘ мало данных».

### Тиры

- **HIGH** (≥ 65) — ставить в проработку немедленно.
- **MEDIUM** (45–64) — держать в поле зрения.
- **LOW** (< 45) — фиксируем, ресурсы не тратим.

## Обновление данных конкурентов

Блок `competitor_matrix` в `data.json` обновляется автоматически:
- **Скрипт:** [`scripts/refresh_competitors.py`](scripts/refresh_competitors.py)
- **Workflow:** [`.github/workflows/refresh-competitors.yml`](.github/workflows/refresh-competitors.yml)
- **Расписание:** каждый понедельник 06:00 UTC (09:00 МСК)

Ручной запуск: Actions → Refresh Competitor Matrix → Run workflow.

При падении парсера (изменился HTML банка, антибот и т.д.) автоматически
создаётся issue с меткой `bug, automation`, а данные в матрице
помечаются как `stale` (в UI появляется янтарный бейдж).

**Стратегия — manual-first.** В day-0 все парсеры кроме `_parse_psb_military`
задизейблены как scaffold. Включать по одному, сверяя селекторы с живыми
страницами банков. Так модель гарантирует, что sky не свалится в
некорректные данные из-за смены вёрстки на одном сайте.

## Обновление data.json → index.html

Данные в двух местах: `data.json` (мастер) и inline внутри `index.html`
(для self-contained-режима). После изменения `data.json` — прогнать
однострочник, чтобы засинхронить HTML:

```bash
python -c "
import json, re
d = open('data.json', encoding='utf-8').read().strip()
h = open('index.html', encoding='utf-8').read()
h = re.sub(r'const DATA = \{.*?\};\s*\n</script>', 'const DATA = ' + json.dumps(json.loads(d), ensure_ascii=False, separators=(',',':')) + ';\n</script>', h, count=1, flags=re.DOTALL)
open('index.html', 'w', encoding='utf-8').write(h)
"
```

Или (лучше) сделать pre-commit hook.

## Ограничения

Явно фиксируем, что модель НЕ может:

- Предсказать факт заключения контракта. Скор HIGH ≠ сделка.
- Учесть личные связи, лоббизм, аппаратные решения — они не в прессе.
- Работать с закрытыми ведомствами (ФСБ, СВР) — публикаций критически
  мало, скор считается на основе гипотез плейбука.
- Отличить реальное намерение закупить от плановой ротации бюджета.
- Заменить коммерческую проработку с ЛПР ведомства.

Долевые оценки конкурентов (`market_shares`) — публичные
аппроксимации. Для боевого использования нужны платные отчёты Frank RG
или внутренняя CRM-статистика Сбера.

## План развития

**Итерация 2:** калибровка весов формулы на исторической выборке
закрытых сделок (100+ размеченных пар «скор → факт»).
**Итерация 3:** переход от статичного словаря событийных триггеров к
LLM-классификатору, дообученному на размеченном корпусе публикаций.
**Итерация 4:** интеграция с внутренней CRM Сбера — вместо публичных
долей рынка использовать фактические данные о сделках.
